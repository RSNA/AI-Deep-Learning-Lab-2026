# Lab 02 game: rules for build sessions

This folder holds the code of the Lab 02 game, a multiplayer browser game played live by a room
of radiologists. Read `docs/ENGINEERING_SPEC.md` before writing code. It is the contract.

The game content is private and lives outside this repository. The lab director's private
folder holds the plan (`PLAN.md`) and the content pack. A build session reads that plan first
to learn the current step, and does one step per session.

## The rule that matters most

**No private content enters this repository.** Not in code, tests, fixtures, snapshots,
comments, commit messages, pull request text, screenshots or recordings.

- Develop and test against `content-demo/`. Use the private pack only through `CONTENT_DIR`, on
  the Mac, for the checks that need it.
- Never copy a sentence, a number, an id or a scenario from the private pack. Write demo
  content from scratch, in the library setting the spec describes.
- Never name the private scenarios, their problems or their answers anywhere in this folder.
- Run `npm run check:no-private` with `CONTENT_DIR` set to the private pack before every merge.
- A screenshot for a pull request shows the demo pack.

## The rules of the code

1. The server owns all state. The client shows views and sends commands.
2. The engine is pure: no clock, no network, no storage, no randomness. Time is an argument.
3. Content is data. Code never names a content id. A new number or text needs no code change.
4. Only `packages/engine/src/project/` turns pack data into something a browser may see, field
   by field. Never spread, pass through or strip a pack object.
5. The client imports `protocol` only. It never imports `content-schema` or `engine`.
6. Every message to a player or the big screen passes its strict schema before it is sent.
7. Every wait is in game time. Nothing reads the wall clock except the server's clock module.
8. Every action works by tap on a phone. Drag is an extra.
9. The page loads nothing from another origin.
10. When the code must differ from the spec, change the spec in the same pull request and say why.

## Working here

- Node 22. npm workspaces. TypeScript in strict mode.
- `npm run dev` runs the demo. `npm run check` must pass before every merge. The other commands
  are in section 12.1 of the spec.
- Build and test on the Mac only. Nothing is built, installed or tested on a server. Ship with
  `scripts/deploy.sh`.
- No secret in the repository: no passcode, no token, no server address. The server is reached
  through the SSH alias `lab02-event`.
- Art is CC0 or made for this project. Fonts may be under the SIL Open Font License. List each
  asset in `packages/client/ART.md` and keep its license file beside it.
- The look is section 11 of the spec: a bright pixel town, a light and a dark theme, thick
  outlines and hard shadows. Build every screen in both themes.
- Tests come with the code they test. An engine rule has a test for every refusal it can give.
- The parity vectors in `packages/engine/test/vectors/` are generated by the scoring tool of the
  private folder (`python3 tools/lab_scoring.py --vectors <file>`). Regenerate them when the
  scoring rules change. Never edit them by hand.

## Git

- Touch only `02-Production-Ready-Agentic-AI-Applications/`. The repository holds seven other
  labs.
- Work on a branch. Open a pull request whose title starts with `Lab 02:`. Squash-merge it
  yourself once `npm run check` passes. The lab director does not review Lab 02 pull requests.
- Keep pull requests to one build step or one fix.

## Closing a step

A build step ends with a play check by the lab director on a laptop and a phone. Fix interface
problems in the same session. Write content problems down for the next content session. The
private plan says how a step is reported and closed.
